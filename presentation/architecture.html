CALDOVA / AGENTIC BANKING01 / 05

Start with the customer outcome: “Move 100 hryvnias from Universal to my savings.” This is not a bot matching a fixed phrase. The model works out what the customer wants, while the application supplies the banking facts and controls what can actually happen.

The important distinction for this conversation is simple: flexible reasoning at the front, deterministic execution at the back. We can make the experience feel natural without asking the model to be the bank’s ledger or its authority to pay.

Transition: here is that separation in the architecture.

REASONING ≠ EXECUTION02 / 05

Follow the request across the slide. The Next.js app receives it and streams the activity to the phone. The model in Microsoft Foundry plans and returns structured function-call requests. The application-side tool call validates arguments, applies customer scope, and invokes the permitted banking operations. Foundry does not open a SQL connection.

SQL holds the sample accounts and ledger; AI Search supplies reference guides. The Service Bus worker is a separate path for events such as salary arriving: it prepares a proposal, not an automatic transfer. We kept one orchestrator rather than splitting into many agents to reduce latency and keep the approval boundary clear.

SEE THE DATA BEHIND THE ANSWER03 / 05

There are two different sources of truth. A balance or transaction question goes through customer-scoped tools to the synthetic banking records in Azure SQL; financial arithmetic is done in application code, not improvised by the model. A product or policy question retrieves passages from indexed reference guides through Azure AI Search.

The customer can click “See the data behind this answer” to inspect the checked fact or retrieved passage and open a full guide. That makes grounding visible rather than just claiming the answer is grounded. The guides are reference content, not live bank terms.

Transition: seeing the data is especially important when an answer leads to an action.

Money movement

A deliberate approval moment.

The same safe pattern covers a top-up, a bill payment, or a transfer between accounts.

01

Understand

02

Verify

Resolve accounts and amounts from real tool results; apply policy checks.

03

Prepare

Persist a precise proposal with destination, amount, and fee.

04

Approve

Only an explicit customer gesture permits transactional, idempotent settlement and a receipt.

No model-generated text is accepted as authorization to move money.

EXPLICIT HUMAN CONTROL04 / 05

For a transfer, the model can interpret “Universal” and “Savings jar,” but the tools resolve the actual accounts and validate ownership, currency, amount, available balance, and destination. The application persists an exact proposal; nothing moves yet.

The customer reviews the source, destination, amount, and fee, then explicitly approves. Only the approval endpoint can execute the idempotent debit and credit and return a receipt. A retry cannot settle the same approval twice. This is where we draw the line: the model may propose; it cannot authorize itself.

START WITH THE CUSTOMER JOURNEY05 / 05

This is live Azure infrastructure rather than a scripted animation: model planning, retrieval, persistent state, event handling, and approval-backed actions all run. It is still a synthetic banking environment: the customers, balances, transactions, and guides are sample material; there is no connection to production core banking.

For a real pilot, we would add end-user authentication and authorization, integrate governed core-banking APIs, move data services behind private networking, and conduct security, compliance, and operational-resilience reviews. We would add more agent or service boundaries only where ownership or scaling warrants them.
